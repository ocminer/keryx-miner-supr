# H16 compatibility in v0.16.0

The defaults match [keryx-node v1.6.7](https://github.com/Keryx-Labs/keryx-node/releases/tag/v1.6.7-PoM)
and upstream miner [d80f3e0](https://github.com/Keryx-Labs/keryx-miner/commit/d80f3e0):
mainnet activates at **DAA 147,000,000**, testnet at **DAA 180,000**. Upgrade solo
nodes and pool nodes to v1.6.7 before activation. The miner follows each job's
DAA; it does not switch by wall clock or a software-version announcement.

## Mining transition

H16 reduces the context pad by exactly 200 MiB in every tier. Model IDs, weights,
pad seed, walk arithmetic and proof encoding remain unchanged. The changed pad
extent changes walk parameters and is consensus-critical.

| Tier | Current pad, MiB | H16 pad, MiB |
|---|---:|---:|
| 0 | 624 | 424 |
| 1 | 3138 | 2938 |
| 2 | 4692 | 4492 |
| 3 | 6320 | 6120 |
| 4 | 2393 | 2193 |

Every job uses its own header DAA score. Below the configured gate, CUDA,
OpenCL/Vulkan and CPU proof construction use the current table. At the gate
and afterwards, they use the H16 table. Old jobs and reorgs below the gate use
the original table again; activation is not latched globally. CUDA and Vulkan
pad caches include the pad size in their keys and release a replaced pad before
allocating its replacement. The model weights stay resident.

For an isolated staging network, `KERYX_PAD_MARGIN_ACTIVATION_DAA` can supply
the same finite gate configured on its node. This is not an automatic network
configuration mechanism. Never substitute a guessed mainnet value. A startup
message prints the configured activation DAA and identifies any override.

## Other upstream H16 rules

| Upstream change | Miner handling |
|---|---|
| Suspension eligibility at the selected parent's DAA and historical windows | Node consensus decides eligibility; miner follows the node's templates and service responses. No local reconstruction of the suspension ledger. |
| Untraced answers do not satisfy audited requests | Existing H15 traced-answer and attention/proof paths remain required. |
| Answer-specific windows | Use actual engine trace dimensions and the canonical traced-response format. Node v1.6.7 removed the proposed prompt-byte-length upper bound on declared prompt positions. |
| One miss per request and uniform strike escalation | Node consensus accounting; no new miner wire format. |
| New audits can extend existing audit deadlines | gRPC refreshes draw, attention and in-flight submission deadlines from `GetAwaitedOpenings`, including increased values. Updated opening deadlines are also persisted. After a restart, accepted traces remain available for authoritative recovery within a bounded audit horizon. Pool mode follows pool opening requests. |
| Ledger catchup/frontier and bounded template-wait fixes | Node implementation changes; use the authoritative templates supplied by the upgraded node. |
| Awaited requests per escrow key | Extend `GetAwaitedOpenings` with escrow key and request hashes. Keep unknown requests queued; discard only requests the node explicitly closes or whose known answer window has ended. |
| Multiple rigs of one address | Rank escrow keys deterministically per request. The first rig starts immediately; siblings wait, recheck the node, and take over when needed. |

The PoM v5 arithmetic, model catalogue and verifiable-inference library remain
unchanged; the RPC/protobuf schema gains request-status fields. Queued requests,
in-flight inference/replay and response retries survive a transient solo-node
reconnect within the same miner process. Restarts restore persisted trace custody
and opening deadlines. Existing platform limitations remain; Metal H15/H16
mining is not supported.

Solo inference uses the selected GPU. When restoring its full inference context,
the NVIDIA backend tries progressively smaller contexts with compute-buffer
headroom. Audit replay still requires room for every token in the original trace.
Pool bridges must relay `mining.ai_response` trace commitments, `mining.ai_draw`
and `mining.ai_opening`; opening messages can exceed 100 KiB.

## Validation status

The source includes frozen pad-table checks, boundary/reorg selection checks and
an ignored CUDA regression that crosses a finite staging gate in one process,
checks pad reuse/replacement and compares GPU results with CPU proofs. On 2026-11-05, native CUDA checks passed on RTX 3070 (fast and fallback paths)
and RTX 5080. Full miner processes with the cached tier-0/tier-2 models crossed
the staging gate, continued above it, rolled back below it and crossed again.

The same cards also passed H16 traced-answer and independent proof verification,
tampered-root rejection, trace custody upload/fetch after restart, attention
openings and mining resumption. Those checks used a loopback fixture with a
finite staging gate; they do not establish live H16 network acceptance. Physical
AMD, Windows GPU and legacy NVIDIA H16 transitions were not tested in this
session. Final release checks additionally cover the official default gate and
solo RPC compatibility with the released node; their results are recorded in
the release notes.
